# Алгоритмы системы

Система содержит два независимых алгоритма:

1. **Распределение нагрузки** — какой преподаватель ведёт какой workload.
2. **Генерация расписания** — на какую дату, какую пару, в какую аудиторию.

Оба реализованы на бэкенде (Fastify + mysql2) без внешних сервисов.

---

## 1. Распределение нагрузки

### 1.1. Постановка задачи

Дано:

- **Workload'ы** W = {w₁, ..., wₙ}: дисциплина, тип (LECTURE / PRACTICE), количество пар, список групп.
- **Преподаватели** T = {t₁, ..., tₘ}: компетенции (дисциплины, которые может вести), опциональный `maxPairs`.
- **Компетенции** C ⊆ T × D.

Требуется найти назначение A: W → T, такое что:

- каждому workload назначен компетентный преподаватель;
- нагрузка не превышает `maxPairs`, если он задан;
- нагрузка распределена равномерно;
- максимум workload'ов назначено.

### 1.2. Класс задачи

Задача относится к NP-трудным задачам о назначениях. Точное решение (ILP, branch & bound) не нужно для интерактивного приложения с 41 workload'ом и 8 преподавателями.

### 1.3. Жадный алгоритм

Реализация: `backend/src/routes/allocation.ts`.

Идея:

1. Сортировать workload'ы: сначала те, у которых меньше кандидатов — «узкие места».
2. Для каждого workload выбрать наименее загруженного из подходящих.

Псевдокод:

```
ВХОД: workloads, teachers, competencies, maxPairs
ВЫХОД: assignment, unassigned

1. qualified ← map disciplineId → [teacherId...]
2. load ← map teacherId → 0
3. sorted ← workload'ы по: кол-во кандидатов ↑, pairs ↓
4. ДЛЯ каждого w из sorted:
     candidates ← qualified[w.disciplineId]
     eligible ← отфильтровать по maxPairs (load[teacher] + w.pairs ≤ maxPairs)
     ЕСЛИ eligible пуст:
         unassigned.add(w)
         ПРОДОЛЖИТЬ
     chosen ← argmin по load среди eligible
     assignment[w.id] ← chosen
     load[chosen] += w.pairs
5. ВЕРНУТЬ assignment, unassigned
```

Сложность: O(n log n + n·k), где k — среднее число кандидатов. Для n = 41 и k ≈ 2 — порядка 200 операций, миллисекунды.

### 1.4. Критерии качества

| Критерий | Как достигается |
|---|---|
| Fairness (равномерность) | argmin по текущей нагрузке |
| Skill match | Жёсткое ограничение — только компетентные |
| Coverage | Эвристически, но не гарантирован оптимум |
| maxPairs | Жёсткое ограничение, если задан |

### 1.5. Ограничения и улучшения

Ограничения:

- не гарантирует оптимум (жадность);
- не учитывает предпочтения преподавателей;
- порядок сортировки при равных условиях влияет на результат.

Возможные улучшения:

| Метод | Что даёт | Цена |
|---|---|---|
| ILP | Оптимум | Сложность, время |
| Генетический алгоритм | Лучшая fairness | Настройка |
| Учёт предпочтений | Fairness по желаниям | Новая таблица |

### 1.6. Тестирование

Покрыто unit-тестами (Vitest):

- базовый сценарий (единственный кандидат);
- отсутствие кандидатов;
- балансировка между двумя;
- соблюдение `maxPairs`;
- приоритизация узких workload'ов;
- детерминизм;
- пустой вход.

## 2. Генерация расписания

Реализация: `backend/src/routes/schedule.ts`.

### 2.1. Постановка задачи

Дано:

- набор workload'ов с назначенными преподавателями (из шага 1);
- семестр 01.09.2026 — 26.12.2026 (16 недель, пн–сб);
- 6 пар в день (08:20, 10:05, 12:20, 14:05, 15:50, 17:35);
- список аудиторий.

Требуется расставить пары по датам так, чтобы:

- у одной группы не было двух пар в один слот (дата + номер пары);
- у одного преподавателя не было двух пар в один слот;
- одна аудитория не использовалась дважды в один слот;
- пары были равномерно распределены по семестру.

### 2.2. Алгоритм

1. Построить список дат семестра, сгруппировать по неделям (`buildSemesterDates`).
2. Для каждого workload вычислить, сколько пар ставить на каждой неделе (`computePairsPerWeek`):
   - если `pairs ≤ weeks` — по одной паре в неделю с начала семестра;
   - если `pairs > weeks` — базовая по 1 плюс остаток, раскиданный по семестру.
3. Для каждой пары искать лучший слот `(дата, номер пары, аудитория)`:
   - группы свободны, преподаватель свободен, аудитория свободна;
   - `score = maxDayLoad * 1000 + pair`, где `maxDayLoad` — текущая загрузка дня;
   - брать слот с минимальным score.
4. Фиксировать занятость в `busyGroup`, `busyTeacher`, `busyAudience`, `groupDateCount`.
5. Если слот не найден — workload попадает в отчёт `clipped` (создано меньше, чем хотели).

Ключевое: `groupDateCount` считает пары по конкретной дате, а не по дню недели. Иначе после 6 пар в понедельник первой недели понедельник блокировался бы на весь семестр.

### 2.3. Сложность

O(n · W · D · P), где n — число пар, W — недель, D — дней, P — пар. Для семестра 16 недель, 6 дней, 6 пар — порядка 700 · 16 · 36 ≈ 400 000 операций, работает за секунды.

### 2.4. Ограничения

- `MAX_PER_DAY_HARD = 6` пар в день на группу;
- если аудиторий мало, часть пар не встанет (например, при 2 группах и 1 аудитории параллельные практики невозможны);
- при большом числе нагрузок возможны `clipped` — попадают в отчёт «Расписание создано с потерями».

### 2.5. Тестирование

E2E (Playwright): логин админом → генерация → проверка, что сумма созданных пар совпадает с суммой `pairs` по всем workload'ам; визуальная проверка, что пары не лепятся в один день недели.
