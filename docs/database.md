# Проектирование базы данных

## 1. Выбор СУБД

Для системы выбрана **MySQL 8.0**:

| Критерий | Обоснование |
|----------|-------------|
| Открытость | Бесплатная, open-source |
| Распространённость | Широкая поддержка, множество инструментов |
| Транзакции | InnoDB поддерживает ACID и внешние ключи |
| Производительность | Достаточно для учебного заведения |
| Кодировки | Полная поддержка UTF-8 (utf8mb4) |

## 2. Нормализация

Схема приведена к третьей нормальной форме (3НФ).

### 1НФ: атомарность

Все атрибуты атомарны.

### 2НФ: полная зависимость от ключа

Все неключевые атрибуты зависят от всего первичного ключа. Промежуточные таблицы `competencies`, `workload_groups` решают M:N-связи.

### 3НФ: отсутствие транзитивных зависимостей

Неключевые атрибуты не зависят от других неключевых.

## 3. Сущности

| Сущность | Описание |
|----------|----------|
| `teachers` | Преподаватели |
| `disciplines` | Учебные дисциплины |
| `groups` | Студенческие группы |
| `competencies` | Компетенции (M:N) |
| `workloads` | Единицы нагрузки |
| `workload_groups` | Связь workload с группами (M:N) |
| `allocations` | Назначение workload на преподавателя |
| `users` | Пользователи системы |
| `audiences` | Справочник аудиторий |
| `schedule` | Конкретные пары расписания |

## 4. Связи

| Связь | Тип | Реализация |
|-------|-----|-----------|
| Преподаватель ↔ Дисциплина | M:N | через `competencies` |
| Дисциплина → Workload | 1:N | `workloads.discipline_id` |
| Workload ↔ Группа | M:N | через `workload_groups` |
| Workload → Allocation | 1:1 | `allocations.workload_id` (UNIQUE) |
| Преподаватель → Allocation | 1:N | `allocations.teacher_id` |
| Пользователь → Преподаватель | 1:1 (опц.) | `users.teacher_id`, ON DELETE SET NULL |
| Workload → Schedule | 1:N | `schedule.workload_id` |
| Audience → Schedule | 1:N | `schedule.audience_id` |
| Teacher → Schedule | 1:N (опц.) | `schedule.teacher_id` |

## 5. Типы данных

| Поле | Тип | Обоснование |
|------|-----|-------------|
| `id` | `VARCHAR(25)` | Формат nanoid (21 символ + запас) |
| `full_name`, `name` | `VARCHAR(150)` | Достаточно для ФИО и названий |
| `email` | `VARCHAR(150)` | RFC 5321 ограничивает 254 символами |
| `password_hash` | `VARCHAR(255)` | Argon2id генерирует ~96 символов |
| `initial_password` | `VARCHAR(50)` | Открытый пароль (для отображения админу) |
| `role` | `ENUM('ADMIN','STAFF')` | Ограничение на уровне БД |
| `max_pairs`, `pairs` | `INT` | Целые числа |
| `type` | `ENUM('LECTURE','PRACTICE')` | Ограничение домена |
| `pair_number` | `TINYINT` | Маленькое целое (до 127) |
| `date` | `DATE` | Дата без времени |
| `created_at`, `updated_at` | `DATETIME` | Автозаполнение |

## 6. Индексы

| Индекс | Обоснование |
|--------|-------------|
| `PRIMARY KEY` | Быстрый поиск по id |
| `UNIQUE` на email, name | Защита от дублей |
| `competencies.uq_teacher_discipline` | Защита от дублей компетенций |
| `schedule.uq_sched_audience_time` | Аудитория не занята дважды |
| `schedule.uq_sched_teacher_time` | Преподаватель не занят дважды |
| `FOREIGN KEY` | Автоматически индексируются |

## 7. Ограничения целостности

### 7.1. Внешние ключи с каскадами

| Правило | Где | Обоснование |
|---------|-----|-------------|
| `ON DELETE CASCADE` | `competencies` → `teachers`, `disciplines` | Удалили родителя — потомки не нужны |
| `ON DELETE CASCADE` | `workloads` → `disciplines` | Удалили дисциплину — workload'ы исчезают |
| `ON DELETE CASCADE` | `workload_groups` → `workloads` | Удалили workload — связи с группами |
| `ON DELETE CASCADE` | `allocations` → `workloads`, `teachers` | Назначение не может существовать без родителя |
| `ON DELETE SET NULL` | `users.teacher_id` → `teachers` | Удалили преподавателя — user остаётся |
| `ON DELETE CASCADE` | `schedule` → `workloads` | Удалили workload — все его пары |
| `ON DELETE RESTRICT` | `schedule` → `audiences` | Нельзя удалить аудиторию, если на неё есть пары |
| `ON DELETE SET NULL` | `schedule` → `teachers` | Удалили препода-замену — пара остаётся |

### 7.2. UNIQUE-ограничения

- `teachers.email`, `disciplines.name`, `groups.name`, `audiences.name`
- `competencies (teacher_id, discipline_id)`
- `allocations.workload_id`
- `schedule (date, pair_number, audience_id)`
- `schedule (date, pair_number, teacher_id)`

## 8. Кодировка

Все таблицы — `utf8mb4_unicode_ci`.

## 9. Расписание

**Таблица `schedule`** хранит конкретные пары — каждую отдельно.

### Почему каждая пара — отдельная запись

В семестре лекция идёт 18 раз. Это не одна запись «повторяется 18 раз», а 18 отдельных строк. Каждая со своей датой.

**Преимущества:**

- перенести одну пару, не трогая остальные;
- заменить преподавателя на одну пару (через `teacher_id`);
- отменить одну пару (удалить запись).

### Особенности

**`teacher_id` — опциональный.** Если NULL — преподаватель берётся из `allocations`. Если задан — это замена на конкретную пару.

**UNIQUE-ограничения:**

- `(date, pair_number, audience_id)` — одна аудитория не может быть занята дважды;
- `(date, pair_number, teacher_id)` — один преподаватель не может быть в двух местах.

**FK RESTRICT на аудитории** — нельзя удалить аудиторию, если на неё есть пары.

## 10. Пароли преподавателей

В таблице `users` есть поле `initial_password VARCHAR(50) NULL`. Оно хранит пароль в открытом виде и предназначено для отображения администратору.

- **При создании преподавателя** — генерируется случайный пароль, сохраняется в `password_hash` (argon2) и дублируется в `initial_password`.
- **При смене пароля преподавателем** — `password_hash` обновляется на новый хэш, `initial_password` — на новый пароль. Админ всегда видит актуальный.
- **У администратора** `initial_password = NULL`.

Это компромисс для учебного проекта: в продакшне так делать нельзя (нарушает базовую безопасность argon2), вместо этого используют функцию сброса пароля через email или одноразовые ссылки.

## 11. Итог

Схема БД:

- соответствует 3НФ;
- использует FK и каскады для целостности;
- имеет UNIQUE для защиты от дублей;
- оптимизирована индексами.
